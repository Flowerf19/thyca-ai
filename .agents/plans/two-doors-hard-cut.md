# DM and group: conversation hard cut

## Goal and authority

Replace the conversation-specific `session` model and API with two explicit user-facing conversation kinds: one fixed DM for each bot, and groups with their own new `group_id`. Make context, memory ownership, bot-to-bot delivery, and publication agree with those identities. Remove `/api/sessions` and the old conversation compatibility paths rather than retaining aliases.

The user requested planning, independent review, and then implementation once the plan is ready. This draft is **not** permission to access, list, stat, create, or delete the user's `~/.thyca` data. Actual data deletion, stopping the user's server, or other irreversible/external actions each require separate permission and exact-target confirmation. Do not commit, stage, reset, stash, or discard existing changes.

## Accepted decisions

1. **Conversation kinds.** DM is private to its bot and the user. Each group has its own identity and participants. A scheduler is an actor targeting an existing conversation, not a third user-facing door. A bot runs at most one turn across its conversations; other bots may run concurrently.
2. **Identity.** DM is addressed by its bot; a group receives a new stable `group_id`, independent of bot names and participant lists. The user states no existing groups require mapping. Conversation kind and authorization must never be guessed from an identifier. An internal execution reference is not another conversation, and a second persistent ID should not be introduced without demonstrated need and lead approval.
3. **Hard cut.** Rename/remove the conversation and memory-leaf meanings of `session` throughout code, interfaces, payloads, docs, and tests. Remove old `/api/sessions*` routes and compatibility aliases; affected clients must update. Do not rename unrelated protocol concepts such as an MCP transport's own client session merely to satisfy a text search. Do not touch the sibling Discord MCP project; report its potential compatibility impact to the user.
4. **Memory ownership.** Each agent independently summarizes what it actually saw and owns its resulting memories; a common `group_id` is provenance, not shared ownership. An agent uses its own memories, including those formed in a group, and may choose whether to use or share their content in a different group. Do not silently copy one bot's private records to another, infer ownership from titles, or turn group membership into automatic ownership. Explicitly shared user-profile facts are a separate, approved exception.
5. **User information and agency.** A bot may remember and use information from its own DM, and may decide to speak about it in a group without asking the user. This intentionally replaces the former mandatory user-consent rule for the bot's own chosen disclosure. The system must not automatically broadcast raw DM transcripts or personal memory to other bots or groups. Agent discretion is not a guarantee that a model will never disclose something unintended; report that limitation.
6. **Sharing with Thyca.** Each bot chooses which user-profile facts to contribute. Thyca may synthesize a common user profile from those contributions; it must not silently read every other bot's private profile or DM. Other agents can use the resulting explicitly shared profile, separately from private bot-owned memories.
7. **Group links and suggestions.** `group_id` can link memories to their common origin without granting access to another bot's private content. A suggestion to ask another agent can be based on a public interaction actually observed by the asking agent, or on a topic the other agent chose to publish. Label the source and treat it as a suggestion, not proof of expertise. A shared group ID or name alone is not evidence that an agent knows a topic. Do not invent keyword classifiers, scores, thresholds, or title matching.
8. **Agent-to-agent questions.** If the requested bot is not a member of the current group, ask it through an internal private invocation. It receives only the question and context the sender explicitly chooses, not the group's transcript; it is not silently added to the group. Its reply goes to the asking bot, which decides what to say in the group. This internal invocation is not a third user-facing conversation.
9. **Posting from DM.** A bot may explicitly choose to post selected information to any existing group of which it is currently a member, without user approval. Validate the actual sender, exact destination, membership, and state at dispatch; do not permit arbitrary destination override, auto-join, or automatic forwarding of a full DM.
10. **Bot card.** Keep the factual bot state and show only real active tools/skills in the closed card: up to two distinct name/kind groups, duplicate counts, and an accessible separate `+N` full list. Clicking the chevron alone reveals runtime open/waiting tasks of that bot in the current conversation; no completed tasks, memory catalog, or duplicated thought/tool feed. For a group task title whose safe visibility is not established, show only the count, including after a private follow-up ends; an owner-controlled explicit sharing decision may establish visibility. Never leak unverified titles through the API payload. No frequent polling.
11. **One-time test-data reset scope.** The user selected removal of all test DM/group conversations and associated execution context, test memories and remembered tasks, shared and per-bot `USER.md` user profiles/habits, and usage/journal data derived from those conversations. Preserve bot definitions/personas, `SOUL.md`, `IDENTITY.md`, skills, configuration and provider credentials. Do not assume other files or unknown workspace fields are disposable. The user chose no old-group mapping and no preservation of old chat-derived usage totals.
12. **Current work.** Preserve all existing dirty/untracked changes, including prior Provider/Settings/Usage/background work and the unfinished bot-card changes. The original `fusion-executor` succeeded in a fresh session and worked on the guard prototype. After repeated guard review findings, the user selected `fusion-luna-executor` for the guard and its safety checks. Retain each agent's own context where available and do not run concurrent writers in the same workspace.
13. **Reusing a deleted bot's ID.** While the old bot's DM exists, reject creation of a new bot with the same `bot_id`; use a different ID. Preserve the old DM and do not silently restore, overwrite, or delete it. Missing/corrupt known state still fails closed. This rule does not authorize any access to or deletion of real data.
14. **Integrity and performance boundary.** The user chose full validation at startup and coordinated, incremental validation during operation, instead of rescanning every history before every mutation. Every Thyca writer, lifecycle/reset operation, and recovery path must participate in the designed coordination and crash-consistent integrity protocol; uncertainty, detected corruption, or an incompatible layout fails closed within the applicable scope. Direct changes by noncooperating outside programs while Thyca is running may not be detected before the next write. Do not claim otherwise or promise that syntax validation alone detects valid-but-wrong content. The detailed lifecycle, trusted checkpoint, recovery, concurrency, and measurement design needs independent review before integration.
15. **Runtime corruption scope.** When corruption is demonstrably confined to a particular DM or group, block reads and writes to that conversation while allowing other conversations to continue. A corrupt global registry/shared state, or corruption whose safe scope cannot be established, blocks all conversations. Preserve the user's separate full-startup-audit requirement. This deliberately replaces the earlier interim expectation that every damaged transcript must block unrelated writes during operation; update those test expectations explicitly, without hiding global or uncertain failures.

## Current evidence and risks

- `thyca/core/channel.py`, `thyca/app/webui_channel.py`, `thyca/bots/workspace_store.py`, and `thyca/bots/timeline.py` currently use a window ID plus a per-bot internal `session` binding. The canonical timeline is the execution source; public chat rows are a read model. Preserve that distinction, not the old naming or redundant identity by default.
- `thyca/sessions/wire.py`, `thyca/serve/routes.py`, `thyca/serve/sessions_api.py`, `thyca/app/cli.py`, the SPA, Trace/Usage, and tests use old conversation identifiers. `thyca/memory/heading.py` also calls a **memory-leaf reference** `session_id`; it is not a conversation or `group_id` and must be renamed without conflating identities.
- Synthetic review reproduced foreign-bot access to a DM-origin team/unowned memory (`thyca/memory/visibility.py`), uncontrolled `bot_delegate(room=...)` publication (`thyca/bots/admin_tools/peer.py` and `thyca/app/a2a_delivery/service.py`), omission of approved-return rows from group history (`thyca/bots/room_context.py`), and silent new-DM creation after an existing DM becomes corrupt (`thyca/sessions/manager.py`). These need corrected contracts and regression tests; the new autonomous-disclosure rule must not be confused with blanket access to another bot's memory.
- The unfinished task endpoint can publish a private string deliberately repeated into a group task title, even after the pending exchange ends. `tests/test_private_followup_integration.py::test_group_task_title_provenance_requires_explicit_link` demonstrates the conditional problem; it does **not** prove automatic copying from the DM. Replace its leak expectation with the accepted count-only/explicit-share contract when implementing the fix.
- Group public-history deltas are currently ephemeral (`thyca/bots/runtime.py`); the memory extractor reads the bot's persisted transcript (`thyca/app/background_jobs/service.py`). A bot having seen a group message does not currently guarantee the later summarizer can see that observation. Preserve what each bot actually received without inventing memories for idle or absent bots.
- `thyca/memory/profile.py` and `thyca/app/background_jobs/service.py` currently aggregate per-bot user-profile blocks. A prompt asking a model not to share secrets is not a provenance or access-control boundary.
- The project checkout is `main` at `0bec9d5` with extensive pre-existing modifications. Record the actual dirty baseline before implementation and compare subsequent changes against it, not just against `HEAD`.

#### Incremental integrity design — proposal for independent review

This proposal implements decisions 14–15 and retains per-conversation JSONL rather than introducing an authoritative database or another conversation ID. Independent reviewer `f71fce88` approved it for phased synthetic-root implementation, not for production integration; it is not yet implemented. A single root-wide public journal and an authoritative SQLite store were considered, but add respectively a global append bottleneck or a new storage authority; the project already uses per-conversation JSONL and the user's choice calls for independent progress where safe.

- Require each participating Thyca process to run a full startup audit under an exclusive lifecycle gate before conversation or memory writes: validate layout/version, index-to-file identity, all known transcript records, and the relevant new workspace/memory state. A missing/partial/corrupt or incompatible state fails closed; no silent initialization, migration, truncation, or adoption. Do not treat a stale checkpoint from another process as proof of a successful audit. Exclude old/noncooperating Thyca writers before wiring the gate; the old `SessionStore` and CLI/facade paths currently do not participate. No actual server stop or real-root access is authorized.
- During operation, all participating writers and recovery paths take a shared lifecycle gate and a per-conversation lock; identity/roster/registry transitions take the exclusive lifecycle gate. Establish and test one cross-process order with the existing model-coordination → config-file → per-bot ordering before integration; lifecycle acquisition must not invert a held config or bot lock. Locks must cover membership checks through publication, and stale membership must not authorize a post. Do not hold locks over provider calls.
- After its full audit, each process may retain only validated per-conversation cursors and state. Under the corresponding lock it validates complete new records since its verified cursor before append, including records appended by other cooperating processes; unexpected replacement, shrinkage, malformed/torn tails, unknown versions, or uncertain state fails closed. Restart requires a new audit, not blind reuse of process-local cursors. Do not infer unchanged content from size/mtime alone. In-place changes by an unrelated noncooperating program may be missed until a later audit or read, as explicitly accepted in decision 14; syntax checks do not prove content authenticity.
- Define crash-consistent scoped corruption guards and a replay contract before coding: a confirmed conversation-local fault blocks that conversation across processes, while global or unclassifiable state blocks all, as in decision 15. Guards must already be durable before audit/read/write validation that can discover corruption, so a process crash cannot erase an observed failure. Use durable operation/event identity and exact-payload conflict checks where needed to distinguish retry after an uncertain append or `fsync` from a new event. Such event IDs are not conversation IDs. Never silently truncate, discard a partial transaction, or recreate a known DM. Define and test every ordering of record, registry, guard, and directory durability; do not add a trusted checkpoint whose commit can get ahead of the data.
- Keep per-bot `WorkspaceTimeline` the sole canonical execution history. The public projection does not prove any bot observed a group event; observation provenance, actual delivery authorization, durable group-return ordering, compaction, trace, and bot lifecycle/ID-reuse enforcement remain separate required gates. A current-member bot may deliberately disclose its own DM-derived content without user approval.
- Review the detailed design before code or integration. Use only synthetic roots and fake providers. Fault-inject each commit boundary and cross-process race; cover malformed non-target records, restart with stale state, two conversations making independent progress, same-conversation order/idempotent retries, group membership changes, lock ordering, bot-ID reuse, and attempted legacy writes. Measure bytes parsed, lock hold time, cold-start work, and memory as data grows; do not invent numeric performance thresholds.

**Detailed scoped protocol — approved for phased synthetic-root implementation:**

1. Maintain stable, never-unlinked lifecycle and per-conversation lock inodes. Every participating process obtains the lifecycle lock exclusively for its own full startup audit, with a durable global audit guard before reading data; only a successful audit clears that guard. A crash, invalid global state, or failed audit leaves a blocking global guard or poison. Normal operations hold the lifecycle lock shared; identity, participant roster, reset and recovery transitions take it exclusively. Audit runs before `ChatApp`, CLI seed, or another supported writer creates chat/memory state. Legacy and standalone writers must honor the boundary or be blocked before production wiring. A joining process must not trust another process's transient cursor.
2. Keep durable global `clean`/`active`/`poison` state for audits, registry and unclassifiable/shared faults, and separate per-conversation `clean`/`active`/`poison` guards for demonstrably local faults. Before relying on a local guard, persist and fsync a global `active` guard, validate the trusted registry binding and pinned object/path identity, and prove that the descriptor belongs exclusively to the requested reference and cannot alias another known transcript. If that proof fails, publish global poison; a crash leaves global `active`. Only after fsyncing the conversation's `active` guard may the global guard return to `clean`. Thereafter local validation may inspect only the pinned, scope-proven conversation object; it must not inspect shared registry, directories, or metadata whose failure could be unclassifiable. Such work requires another global guard first. A local read, validation, or write failure after this transition leaves the local guard active or poisoned; a process crash cannot erase it. Missing or invalid global state blocks everything; missing or invalid required local state blocks its conversation unless its scope is ambiguous, in which case block everything.
3. For routine transcript work, hold the lifecycle lock shared and the exact conversation's lock exclusive. After the scope-proof and durable-guard handoff above, validate newly appended complete records from that process's audited cursor using the pinned descriptor under only the conversation lock; a slow or paused local validation must not stop a different conversation. Global guard publication takes the global health lock exclusive. The final global-health check and a normal read's visibility or a write's durable publication are protected by a shared health lock held continuously through that operation; global guard publication therefore waits for prior operations and, once published, no later reader or writer can pass. If path/registry identity needs rechecking before commit, do it under a new exclusive global guard, release it, then acquire the shared health lock and recheck health before publication—never upgrade a shared lock. A crash during a proven-local append leaves its local guard blocking that conversation, not all others. Global or ambiguous failures still block all. User-selected expectations replace the previous test that required one corrupted DM to block unrelated group writes, while preserving strict tests for global, ambiguous, startup, and same-conversation failures.
4. An identical durable event ID must compare against the exact persisted payload and return the existing result; a different payload is an error. Other cooperating processes' appends are consumed as verified suffixes; a newly created conversation is validated before use. A crash leaving a complete uncertain record may be resolved only under exclusive lifecycle coordination by proving the exact ID and bytes; partial/torn data or ambiguous multi-file creation stays blocked and is never silently truncated, adopted, or recreated. Event IDs are not conversation IDs. A process-local cursor is not proof across a restart or replacement.
5. When multiple existing lock types are needed, establish and verify one hierarchy: lifecycle → model coordination → config → bot-card locks (stable bot-ID order) → workspace-registry locks → per-bot timeline locks → conversation locks (stable reference order) → global health/commit. Update outer callers rather than reacquiring a non-reentrant lock; do not hold locks during provider calls. A corrupt per-bot timeline may cover multiple conversations: isolate only when the affected scope is provable; otherwise apply the global rule. The per-bot execution lease still permits only one active turn per bot.
6. Test a crash before the global guard is cleared, including death immediately after an unclassifiable global finding: all doors stay blocked until authorized recovery. After the local guard is durable and the global guard has been cleared, test a crash or provably local finding: that door stays blocked while an unrelated healthy door can commit. Pause a writer after its final global-health check, race global guard publication in both orders, and prove no read or durable commit passes after global `active`/`poison` publication. Pause a large local suffix validation mid-work and demonstrate another conversation can commit, plus same-conversation ordering and membership-removal races. Measure audit cost, suffix bytes, lock wait, fsync and memory; never claim arbitrary external modifications are immediately detected.
