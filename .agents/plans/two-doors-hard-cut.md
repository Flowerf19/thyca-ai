# DM and group: conversation hard cut

## Goal and authority

Replace the conversation-specific `session` model and API with two explicit user-facing conversation kinds: one fixed DM for each bot, and groups with their own new `group_id`. Make context, memory ownership, bot-to-bot delivery, and publication agree with those identities. Remove `/api/sessions` and the old conversation compatibility paths rather than retaining aliases.

The user authorized implementation work against this plan in sequenced, reviewed handoffs; this checkpoint-specification handoff does not implement markers, schema v2, cursors, runtime wiring, or the hard cut. This plan is **not** permission to access, list, stat, create, or delete the user's `~/.thyca` data. Actual data deletion, stopping the user's server, or other irreversible/external actions each require separate permission and exact-target confirmation. Do not commit, stage, reset, stash, or discard existing changes.

## Accepted decisions

1. **Conversation kinds.** DM is private to its bot and the user. Each group has its own identity and participants. A scheduler is an actor targeting an existing conversation, not a third user-facing door. A bot runs at most one turn across its conversations; other bots may run concurrently.
2. **Identity.** DM is addressed by its bot; a group receives a new stable `group_id`, independent of bot names and participant lists. The user states no existing groups require mapping. Conversation kind and authorization must never be guessed from an identifier. An internal execution reference is not another conversation, and a second persistent ID should not be introduced without demonstrated need and lead approval.
3. **Hard cut.** Rename/remove the conversation and memory-leaf meanings of `session` throughout code, interfaces, payloads, docs, and tests. Remove old `/api/sessions*` routes and compatibility aliases; affected clients must update. Do not rename unrelated protocol concepts such as an MCP transport's own client session merely to satisfy a text search. Do not touch the sibling Discord MCP project; report its potential compatibility impact to the user.
4. **Memory ownership.** Each agent independently summarizes what it actually saw and owns its resulting memories; a common `group_id` is provenance, not shared ownership. An agent uses its own memories, including those formed in a group, and may choose whether to use or share their content in a different group. Do not silently copy one bot's private records to another, infer ownership from titles, or turn group membership into automatic ownership. Explicitly shared user-profile facts are a separate, approved exception.
5. **User information and agency.** A bot may remember and use information from its own DM, and may decide to speak about it in a group without asking the user. This intentionally replaces the former mandatory user-consent rule for the bot's own chosen disclosure. The system must not automatically broadcast raw DM transcripts or personal memory to other bots or groups. Agent discretion is not a guarantee that a model will never disclose something unintended; report that limitation.
6. **Sharing with Thyca.** Each bot chooses which user-profile facts to contribute. Thyca may synthesize a common user profile from those contributions; it must not silently read every other bot's private profile or DM. Other agents can use the resulting explicitly shared profile, separately from private bot-owned memories.
7. **Group links and suggestions.** `group_id` can link memories to their common origin without granting access to another bot's private content. A suggestion to ask another agent can be based on a public interaction actually observed by the asking agent, or on a topic the other agent chose to publish. Label the source and treat it as a suggestion, not proof of expertise. A shared group ID or name alone is not evidence that an agent knows a topic. Do not invent keyword classifiers, scores, thresholds, or title matching.
8. **Agent-to-agent questions.** If the requested bot is not a member of the current group, ask it through an internal private invocation. It receives only the question and context the sender explicitly chooses, not the group's transcript; it is not silently added to the group. Its reply goes to the asking bot, which decides what to say in the group. This internal invocation is not a third user-facing conversation.
9. **Posting from DM.** A bot may explicitly choose to post selected information to any existing group of which it is currently a member, without user approval. Validate the actual sender, exact destination, membership, and state at dispatch; do not permit arbitrary destination override, auto-join, or automatic forwarding of a full DM.
10. **Bot card.** Keep the factual bot state and show only real active tools/skills in the closed card: up to two distinct name/kind groups, duplicate counts, and an accessible separate `+N` full list. Clicking the chevron alone reveals runtime open/waiting tasks of that bot in the current conversation; no completed tasks, memory catalog, or duplicated thought/tool feed. For a group task title whose safe visibility is not established, show only the count, including after a private follow-up ends; an owner-controlled explicit sharing decision may establish visibility. Never leak unverified titles through the API payload. No frequent polling.
11. **One-time test-data reset scope.** The user selected removal of all test DM/group conversations and associated execution context, test memories and remembered tasks, shared and per-bot `USER.md` user profiles/habits, and usage/journal data derived from those conversations. Preserve bot definitions/personas, `SOUL.md`, `IDENTITY.md`, skills, configuration and provider credentials. Do not assume other files or unknown workspace fields are disposable. The user chose no old-group mapping and no preservation of old chat-derived usage totals.
12. **Current work.** Preserve all existing dirty/untracked changes, including prior Provider/Settings/Usage/background work and the unfinished bot-card changes. The original `fusion-executor` succeeded in a fresh session and worked on the guard prototype. After repeated guard review findings, the user selected `fusion-luna-executor` for the guard and its safety checks. Those JSONL guard/journal details are now historical and are superseded as the storage target by the SQLite checkpoint below. Retain each agent's own context where available and do not run concurrent writers in the same workspace.
13. **Reusing a deleted bot's ID.** While the old bot's DM exists, reject creation of a new bot with the same `bot_id`; use a different ID. Preserve the old DM and do not silently restore, overwrite, or delete it. Missing/corrupt known state still fails closed. This rule does not authorize any access to or deletion of real data.
14. **Integrity and performance boundary.** The user chose full validation at startup and coordinated, incremental validation during operation, instead of rescanning every history before every mutation. Every Thyca writer, lifecycle/reset operation, and recovery path must participate in the designed coordination and crash-consistent integrity protocol; uncertainty, detected corruption, or an incompatible layout fails closed within the applicable scope. Direct changes by noncooperating outside programs while Thyca is running may not be detected before the next write. Do not claim otherwise or promise that syntax validation alone detects valid-but-wrong content. The detailed lifecycle, trusted checkpoint, recovery, concurrency, and measurement design needs independent review before integration.
15. **Runtime corruption scope.** When corruption is demonstrably confined to a particular DM or group, block reads and writes to that conversation while allowing other conversations to continue. A corrupt global registry/shared state, or corruption whose safe scope cannot be established, blocks all conversations. Preserve the user's separate full-startup-audit requirement. This deliberately replaces the earlier interim expectation that every damaged transcript must block unrelated writes during operation; update those test expectations explicitly, without hiding global or uncertain failures.

### Storage and identity contract

- Use one SQLite database for the store root. Do not migrate JSONL journals or an existing SQLite layout. Schema v2 is a fresh format; v0, v1, unknown versions, missing state, and incompatible layouts fail closed. No automatic upgrade, shadow write, adoption, truncation, cleanup, or fallback.
- Normal and admin operations open an existing database using SQLite URI `mode=rw`. They never create the root, database, or schema. Only explicit, separately authorized root initialization can create the database. Root audit may cause SQLite to create WAL/SHM sidecars when opening an existing DB, but must not create the root, DB, or schema.
- Bind the database to a canonical `root_instance_id` stored in the DB and in each marker. A replacement DB, marker from another root instance, or mismatched marker is not adopted.
- Schema v2 must carry a singleton root state (`root_instance_id`, `pending|ready`), per-conversation lifecycle state (`pending|ready`), monotonic event `seq`, `logical_seq`, `generation`, and persistent high-water values. A group is created directly `ready`; a DM bootstrap uses `pending` then `ready`. Do not reset/reuse high-water or generation when rows are purged or compacted.
- The root directory may already exist and contain unrelated bot cards, config, skills, or other preserved sentinels. Explicit authorized initialization must work on such a genuinely fresh existing root, leave every unrelated sentinel byte/mode untouched, and create only store-owned artifacts. Existing directory, successful `mkdir`, missing DB/marker, or absence of some artifacts is **not** proof of freshness or authorization. A trusted external lifecycle/reset gate must provide the fresh-root or authorized-reset intent; that gate does not yet exist. If the whole root path is absent, only `initialize` called with that trusted caller's explicit authorization intent may create it; `mkdir` itself does not establish freshness or authorization. The Python intent accepted by this unwired prototype and synthetic tests is not authentication. Do not access, reset, or infer state from real user data. Normal read/audit against a pre-existing sentinel root must fail without creating any store artifact; the same root may be initialized only with explicit authorized intent.

This design incorporates the lead-selected review decisions recorded in `dd2130cb-b228-4cf9-a4e0-e59f9da23aa7` and `9fb04e07-4fa9-42c2-92ec-2721536c9ea3`, including initialization of an existing fresh root by authorized intent, pinned directory admission locking, and the two-phase pending/ready handshake. That design review is not an implementation review.

### Bounded marker layout

```text
<store-root>/
  conversations.db
  conversations.db-wal / conversations.db-shm   # SQLite sidecars when present
  conversations.lock                              # stable; never unlink
  conversations.root.json
  conversations.root.json.tmp                     # deterministic root temp name
  dm-markers/
    <validated-bot-id>.json
    .<validated-bot-id>.json.tmp                  # deterministic per-bot temp name
```

- Root marker exact canonical JSON shape (no extra/missing/duplicate keys):

  ```json
  {"root_instance_id":"<canonical UUID>","state":"pending|ready","version":1}
  ```

- Per-bot marker exact canonical JSON shape:

  ```json
  {"attempt_id":"<32 lowercase hex>","bot_id":"<id matching filename>","dm":"pending|ready","root_instance_id":"<canonical UUID>","version":1}
  ```

- Marker serialization is canonical, sorted, compact UTF-8. With a 36-byte canonical UUID, existing bot-ID grammar capped at 64 ASCII bytes, and 32 lowercase-hex attempt ID, the exact maximum canonical payloads are 89 bytes for the root marker and 210 bytes for a per-bot marker. Reject duplicate JSON keys, unknown fields/versions/states, noncanonical UUIDs, filename/content bot mismatch, oversized/truncated/noncanonical files, and malformed temp names. Never add a global bot-count or lifetime cap and never rewrite an unbounded `bots` array. Per-bot markers are durable known-state/tombstones; their number can grow with bot IDs over time, and filesystem exhaustion must fail closed.
- Temp names deterministically identify their bot. A recognized per-bot temp or malformed marker with a determinable valid bot ID is local to that DM; an unknown/unmappable entry in the marker directory is global audit failure. A root marker temp is global. Unexpected entries in the reserved store namespace (including unknown `conversations.*` artifacts or unknown `dm-markers/` entries) are global audit failures. Audit only that namespace: unrelated root files are not “unknown store entries” and must not be modified. No automatic temp cleanup or recovery.
- Markers are state evidence, not authentication. They cannot prove who wrote them, cannot prove the root is fresh if all store artifacts are removed, and cannot detect every noncooperating same-UID mutation.

### Path handling and lock order

- Preserve the integrated lock hierarchy: `lifecycle → model coordination → config → bot → admission-directory → store-root → SQLite`. The lifecycle component is an external integration gate, not implemented here.
- Before root initialization creates **any store artifact**, it obtains `flock(LOCK_EX)` on an opened, pinned root-directory FD (`O_DIRECTORY|O_NOFOLLOW`) and retains that admission lock through initialization. Then it creates/opens the stable `conversations.lock`, obtains its `LOCK_EX`, and holds it through the final SQLite ready commit. Existing-root initialization uses the same path and must not rely on winning `mkdir` as proof of freshness. Unsupported directory `flock` fails closed; never continue unlocked.
- Store lock inodes are stable and never unlinked. Normal opens do not use `O_CREAT`; missing lock/root/marker/DB is an error. Root initialization and DM bootstrap take the store-root `LOCK_EX`; `VACUUM` also takes `LOCK_EX`. Each ordinary `read`, `append`, `create_group`, `set_metadata`, and `purge` holds store-root `LOCK_SH` together with its SQLite transaction. Each compaction snapshot and final phase separately holds `LOCK_SH` with its SQLite transaction; release both before decoding or calling the summarizer. SQLite begins only after the store lock. Do not reacquire a non-reentrant public lock: public entry points acquire once and call internal locked helpers. No code may acquire the admission-directory lock after the store lock.
- Check ancestors, root and marker directories, DB and SQLite sidecars with no-follow descriptor-relative operations. Validate owner/mode/type, hardlink count, and `lstat`/`fstat` identity on the same opened object; reject symlink/hardlink aliases and unexpected sidecars. Test only within the accepted threat model. Checks do not close every pathname race or stop a cooperating-path-bypassing same-UID writer; state that limitation explicitly.
- A first initializer may leave no artifacts if it crashes before creating the store lock. A later initializer may retry only when its external intent is still genuinely fresh/authorized and it revalidates the store namespace under the directory admission lock. A crash after the store lock exists (lock-only or any later partial state) is fail-closed; do not resume, unlink, or silently clean it. In a 16-process initialization race, losers wait at the directory admission lock, then observe `ready` and return `already_initialized` for the same instance.

### Root initialization and DM bootstrap handshake

Root initialization and per-bot DM bootstrap use two-phase, durable handshakes. All public **and admin** DB operations require both the relevant marker and DB state to be `ready`.

1. **Root initialization:** with the directory admission and store-root `LOCK_EX` held, publish the root marker `pending` (write temp, fsync file, rename, fsync root directory); create the new schema-v2 DB with root state `pending` and commit it durably; publish the root marker `ready` using the same temp/fsync/rename protocol and fsync its parent; then transactionally set DB root state `ready` as the final commit. Keep both exclusive locks through that commit. A ready marker with DB still `pending` is blocked.
2. **DM bootstrap:** require root marker and DB root state `ready`, plus no target marker/temp and no existing target DM row. Under store-root `LOCK_EX`, durably publish the target bot marker `dm=pending`; create the DM row with DB lifecycle state `pending` and commit durably; publish the bot marker `dm=ready` and fsync `dm-markers/`; then transactionally set the DB row `ready` as the final commit. Keep `LOCK_EX` through the final commit. A target row with no marker, a pending marker/row, or one ready and the other not ready blocks that DM; no adoption or automatic completion.
3. If directory fsync fails after the `ready` rename, leave DB state `pending`, even if the ready file is visible. Fsync unsupported/failure is fatal and fails closed; do not silently rename back, delete artifacts, or claim durability. Root init failure is global; per-bot bootstrap failure is local only when root/DB state and target identity are otherwise provable.
4. A commit exception may be commit-unknown. Never retry a mutation. While still holding `LOCK_EX`, resolve only by reading the persisted marker/DB pair: both `ready` means the one operation completed and return its existing result; pending, mismatched, unreadable, or unprovable state remains blocked with a sanitized error. Do not auto-run the remaining handshake or create a second DM. No automatic recovery is part of this checkpoint.
5. The external lifecycle/reset authority that decides who may request root init or per-bot bootstrap is not yet present. Fake intents in tests prove ordering/state transitions only; they are not an authentication mechanism. No runtime wiring, real-data reset, or reset permission is implied.

### Audit and normal-open behavior

- Startup lifecycle integration must run a full root audit before any supported chat/memory writer. In the prototype contract, `audit` first obtains root store `LOCK_SH`, then enumerates `dm-markers/`; it begins one SQLite read transaction before the first DB read used for comparison and uses that same transaction for the entire marker↔DB snapshot. Audit streams markers and DB rows with per-record bounded parsing/memory; total audit work is proportional to the number of conversations and messages and is not claimed to have a global cost bound. This prevents cooperating initializers from changing marker membership during audit and avoids false mismatches between separately sampled DB states.
- Audit can create SQLite WAL/SHM sidecars while opening the existing DB; it must never create the store root, DB, or schema. It requires root and DB `ready`, schema v2, matching instance binding, and valid store-owned entries. A malformed/missing root artifact or unknown marker-directory entry is global. A deterministically attributable bot-marker mismatch blocks that DM only when root, directory, DB schema/instance, and scope are otherwise sound. The lifecycle startup gate remains a separate integration task and is not implemented here.
- Normal DM access checks the global ready root/DB state, the exact target bot marker, the DM row state, and current membership. It does not enumerate every historical bot marker on every operation; startup audit performs the full known-set comparison. Groups use global root/DB readiness and their DB row, not a bot marker. `audit` is not authorization; markers do not prove bot lifetime or actor identity.

### Cursor, generation, and logical ordering

```python
PageCursor(ref: ConversationRef, generation: int, after_logical_seq: int)
```

- Each stored event has a monotonic, non-reused event `seq` and a logical `logical_seq`; retain persistent event/logical high-water values even when rows are intentionally removed. Bind every cursor to exact `ConversationRef` and generation. Reject bool-as-int, invalid/negative fields, and forged cross-reference cursors; membership is checked before returning any stale-cursor result.
- A stale generation yields an explicit resync response only after membership passes. A cursor beyond the logical high-water or not at a retained logical position in the current generation also requests resync. Empty polling pages preserve the incoming cursor exactly; the initial empty view returns `(ref, current_generation, 0)`. No promise to recover messages intentionally purged by retention.
- A compacted summary occupies the logical position of the last event it summarizes and appears **before** the retained suffix. Later suffix events keep their order. Event sequence and logical order are distinct; append keeps its existing `int` return (new event `seq`). `set_metadata` keeps a transactionally consistent full `Conversation` return in logical order.

### Purge and compaction

- `purge_before` validates with `parse_ts` before filesystem access or lock acquisition. Keep one all-or-nothing SQLite transaction for the entire purge: identify affected doors, delete eligible rows, bump each affected door's generation once, restore append-only triggers, and commit. Preserve the existing integer count and API. No batching, partial commits, age/size policy, or automatic purge is specified; retention is safety-only. A very large transaction remains measured debt.
- Compaction reads a raw snapshot and high-water in one read transaction, then releases SQLite/root locks before decoding or invoking an LLM/summarizer. Reject a requested logical position beyond the snapshot high-water before decode/callback; if the prefix is empty, fail before summarize. If prior purge leaves a gap, clamp to the greatest retained logical position `<= requested` and publish the effective position. Under the final commit lock/transaction, revalidate exact snapshot rows and generation, delete only those rows, append the summary event with a fresh event `seq` at the effective logical position, preserve concurrent suffix appends, and bump generation once. Any overlap/change is an explicit conflict with no mutation and no callback retry. Large snapshots/prefixes remain measured debt.
